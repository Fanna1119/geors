# geors: measurements and status (2026-10-09)

A snapshot of every measurement taken so far, what changed, and what is still
open. Paused here; to be continued with the small-container (Docker)
investigation.

**Machine:** MacBook (Apple Silicon), 8 cores, 16 GB RAM, internal SSD.
Docker Desktop VM: 8 CPUs, 7.7 GB, cgroup v2.

**Data:** Germany, Austria, South Africa, Liechtenstein and Andorra
(Geofabrik extracts of 2026-10-08).

## 3. Docker: serving under memory and CPU limits

Image: `geors:latest`, 69.5 MB (`rust:1-slim-bookworm` build stage,
`distroless/cc-debian12:nonroot` runtime). Load: `wrk` with 2 threads and 4
connections, 8 s per mix, run from the Mac host.

Idle memory in the container: **5 MB** (AT+ZA) to **15–22 MB** (with Germany).

**Conclusions:**

- **Serving never ran out of memory**, down to 64 MB (AT+ZA) and 100 MB
  (with Germany).
- **Memory barely changes throughput** between 100 MB and 4 GB. The query
  working set is small, and the kernel reclaims the rest of the mmapped
  index.
- **CPU count is what matters:** 1 → 4 CPUs is roughly 2–3× more text-search
  throughput. Reverse and nearest are cheap either way.

### Data bind-mounted from macOS: do not use for performance tests

Docker Desktop serves bind mounts over virtiofs (FUSE), so every page-cache
miss is a slow round trip. DE+AT+ZA at 1 GB / 1 CPU: full 32 req/s, prefix
**1.2 req/s** (p50 1.5 s, with timeouts). The same test at 4 GB / 4 CPU gave
full 339 req/s. On a Linux host or a Docker volume this effect disappears
(table above). Bind mounts are fine for correctness, not for benchmarks.

## 4. Docker: importing under memory and CPU limits (incomplete)

| Extract | Limit | Result |
|---|---|---|
| Austria 774 MB | 1 GB, 1 CPU | **OK**: ingest 126 s + index writing 137 s (≈ 4.5 min), no OOM |
| South Africa 402 MB | 256 MB, 1 CPU | **Very slow** (stopped): passes 1–3 took 23 s, areas 41–57 s, then pass 4 ran 10+ min (13 s natively with 8 threads) |
| South Africa 402 MB | 128 MB, 1 CPU | not run |
| Austria 774 MB | 512 MB, 1 CPU | not run |
| Germany 4.6 GB | 4 GB, 2 CPU | not run in Docker. Native 2-thread peak is 2.49 GB heap, so it should fit, but see the open issue below |

**Diagnosis so far:** when the container's page cache is much smaller than
the node-coordinate store, import slows dramatically. The store is
memory-mapped, 16 bytes per needed node: 150 MB for South Africa, 2.4 GB for
Germany. Every way's node lookups are random accesses into it.

- **Fixed:** an in-RAM fence index (every 512th id) cut each lookup from ~25
  page touches to 1 id page + 1 coordinate page. South Africa's area phase
  went from 57 s to 41 s, but pass 4 at 256 MB was still slow when I stopped
  the test.
- **Not done:** the native `--threads 1` baseline for South Africa, needed to
  separate "1 CPU" from "memory pressure". I stopped before running it.
- **Possibly a factor:** the PBF itself was read from a macOS bind mount
  (virtiofs) in these tests. Copying it into the volume would remove that
  variable.

Candidate next steps for low-memory imports:

1. Measure the native single-thread baseline (South Africa, Austria).
2. Repeat the container import with the PBF inside the Docker volume.
3. If memory pressure is confirmed: replace random lookups with a
   sort-merge join for way geometry (fully sequential I/O, the approach
   osmium uses for small RAM), or add a "low memory" mode.
4. Recommended deployment regardless: import on a larger machine or in CI,
   and ship the finished partitions to the small server. Partitions are
   portable between little-endian machines (x86-64, arm64), and serving from
   read-only data now works.

## 5. Changes made in this session (uncommitted)

**Resource controls:**

- `--threads N` / `GEORS_THREADS`, a global flag that sizes everything:
  - the rayon pool (decoding, index writing)
  - the tantivy indexer (at most 4 threads)
  - the server's search pool (`max_blocking_threads`; tokio's default was 512)
  - tokio workers (at most 2)

  Without the flag, it defaults to the CPUs available, which respects
  container CPU limits.
- `--index-memory-mb` / `GEORS_INDEX_MEMORY_MB`: the tantivy indexing budget
  (default 48 MB per thread, minimum 15 MB).

**Import memory:**

- The writer builds its sort keys while scanning the spill file, instead of
  materialising a 40-byte entry per place first (~1 GB less for Germany).
- R-tree boxes are now **f32**, rounded outward so a query never misses a
  candidate. Lower bounds for nearest-neighbour search have 1 m of slack.
  Germany's `spatial.idx` went from 901 MB to 501 MB.
- Node-coordinate fence index (section 4).

**Serving:**

- The spatial candidate set is adaptive: a sorted id list when sparse, a
  bitmap when dense. A 3 km radius in Germany is a few kB instead of a 3 MB
  bitmap per query.
- **Read-only data works:** the tantivy index is opened through a read-only
  directory with no lock files. This was found in Docker: with `:ro` mounts,
  the server failed with "Failed to acquire Lockfile: Read-only file system".
  A regression test covers it.

**Packaging:**

- `Dockerfile` (multi-stage, distroless, non-root uid 65532, `/data` volume,
  `GEORS_DATA` and `GEORS_BIND` preset) and `.dockerignore`.

**Also earlier in this session:**

- South Africa import.
- Synonyms moved to `synonyms/*.toml`, with the `geors synonyms` command.
- `prune_originals` and automatic cleanup of leftovers.
- Diff updates (OSC parser, PBF writer, streaming merge).

**Index format:** now **v7** (f32 R-tree). All partitions in `data/` were
re-imported at v7.

**Test status:**

- Last full run: **70 passed, 0 failed**, plus the new read-only test.
- After the fence-index change, only the `nodes` tests ran (3 passed). The
  Liechtenstein export was byte-identical to the previous build.
- Still to run: the full suite and clippy.

## 7. Answer to "how would it run in a 100 MB – 4 GB, low-core container?"

**Serving:** works at 100 MB with all three countries loaded (measured,
never out of memory). Expect ~250 full-address searches/s per CPU core with
Germany loaded, ~1,000/s for Austria-sized data, and thousands of
reverse/nearest lookups per second. Use a local volume, not a macOS bind
mount. Set `--threads` to the cores you give it.

**Importing:**

- **Small/medium countries** work in modest containers. Austria completed at
  1 GB / 1 CPU in ~4.5 min.
- **Germany** needs ~2.5 GB of heap with 2 threads (measured natively), so a
  4 GB container is the practical minimum.
- **Very small containers (≤256 MB)** become extremely slow to import even
  mid-size countries. The investigation is paused there (section 4).
- **Recommended:** build the index elsewhere, serve it from the small
  container.
